How it works

How the tools are built

The tools are small on purpose. Underneath, they follow a few plain rules so each one is quick to build and straightforward to test.

Code checks what a model returns

Where a tool uses a model, it is limited to picking from options code supplies or reading one fact at a time. Code then checks what comes back before showing it to you.

  • In the funding watch, Cloudflare's Clairic and Clef models extract single facts and fixed options rather than prose. Code then checks that every date, amount and area appears in the funder's page text, and only quotes a sentence if it matches word for word.
  • In the iPhone Label tool, the nutrition figures have to add up.
  • Every tool is allowed to answer "I can't tell". Refusals are counted separately from errors, and gaps aren't filled in with a guess.

Every model is named and pinned

For local tools, Kettle records every model file by its revision, byte size and SHA-256 hash alongside the job it does. Setup checks every download against those hashes, so a pinned tool behaves the same way next year and costs nothing per run. Where a cloud tool uses a hosted model, it logs the reported version alongside every fact. Every tool page lists its models, or says it uses none.

Testing on real files first

Every new tool starts with a written test on real files before any interface is built.

  • The bar to beat is set up front, never weaker than the obvious alternative.
  • Expected answers are marked blind and scored once, on files the method wasn't tuned against.
  • Ideas that don't beat the bar get dropped: Kettle binned a committee watch, a funding calendar and the language model in Media, and publishes the results either way.

Mac, iPhone and the cloud

On a Mac
One desktop app holds the tools. Each tool keeps its own code, models and tests, and runs on its own. A template spins up a new tool, and a linter checks every one.
On an iPhone
Shared packages handle the camera, reading aloud and the clipboard, so a new tool is mostly what it captures and what it checks. That took the app from scratch to three tools and 252 tests in five weeks.
In the cloud
Both cloud tools share one reader for public pages. Each tool is about 260 lines with no extra dependencies, running on a schedule as a Cloudflare Worker.

Shared code is only pulled out once a second tool actually needs it, not ahead of time.

Checking where data goes

  • On a Mac, setup is the only time a tool uses the network. Tables was tested with macOS blocking all outside connections.
  • The Mac tools listen only on localhost, check where every request comes from, and run under a strict content security policy.
  • The iPhone app has no networking code at all.
  • The cloud tools only read public pages. Nothing private ever goes to them.
