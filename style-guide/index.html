Kettle style guide

Small local tools, with work you can see, check and finish.

A guide to the app’s visual language and behaviour, using Kettle’s existing GOV.UK theme. These examples render with the website’s own theme; the app source remains authoritative for each tool’s layout and behaviour.

Principles

Start with the task

Say what the person can finish. Name the models and their jobs separately, where people can inspect them.

Make work explicit

Choosing a file does not start reading it. Label the action that starts work, show its status and provide Stop when cancellation is supported.

Keep the source close

Put the original beside the draft. Let people correct values and preserve empty cells, rather than filling gaps with guesses.

Review before saving

Make review an explicit step. Changes to a reviewed result must clear its review state before another reviewed export.

Local operation, setup downloads and any configured source fetching need accurate, separate explanations. State what the tool actually reads and writes.

Marks and motion

The kttl wordmark and geometric cup identify the app. Keep icons subordinate to visible labels. The existing header above uses the site’s lockup at a 40px height.

In the app, steam is hidden at rest and animates while work is running. Reduced motion shows static steam during work. Status must also appear in words; motion alone never explains what is happening.

Colour

Navy text on pale blue and white, with one blue for actions. Swatches below use the live theme tokens, not a separate palette.

  • Ground #edf2f7 · --k-ground App background
  • Paper #ffffff · --k-paper Cards and working surfaces
  • Ink #16335b · --k-ink Primary text and dark chrome
  • Grey #54677f · --k-grey Secondary text
  • Rule #c9d3e0 · --k-rule Dividers, never text
  • Interactive #2f6fd0 · --k-interactive Primary buttons and focus
  • Interactive text #1d55b0 · --k-interactive-text Links on light surfaces
  • Tint #e0eafa · --k-tint Quiet notices and tags
  • Highlight #00e5e5 · --k-highlight Cyan details on navy
  • Boundary #00e5e5 · --k-boundary Privacy rule on navy
Colour supports meaning. Use words such as “Needs review” or “Could not read the image”. Keep cyan on navy and use the grey token for muted text, rather than reducing opacity.

Errors use the theme’s GOV.UK error treatment ($k-error: #b02a2a). The theme also retains success and pending colours for evidence states. Ordinary uncertainty is a review instruction; it is not automatically an error or a claim of confidence.

Typography

Use system fonts: system-ui, -apple-system, "Segoe UI", Helvetica, Arial, sans-serif. Use the monospace stack for filenames, elapsed time and raw values. No downloaded font is needed.

Cards

White paper, a soft border, a light shadow and --k-radius (16px).

Inner panels

--k-radius-soft (10px) for inset surfaces. Buttons and tags use --k-radius-pill.

Keep the task’s width bounded. Let controls wrap, stack source and result when space is tight, and contain wide tables in a labelled scroll region.

File selection and correction

Use the established file-picker pattern: a real, labelled file input with an optional drop target. State accepted types and limits. Keep previews, validation and unsaved-work decisions with the tool.

Correction fields need visible labels or precise accessible names, such as row and column coordinates. Show errors near the field and use a summary for failures that need attention. Keep the source available throughout review.

Voice

Plain British English. Lead with the person’s task, name the consequence of an action and distinguish a draft from something reviewed.

Actions
“Read this table”, “Stop”, “Save reviewed CSV”. Use a verb and its object where that makes the result clearer.
Uncertainty
“Check this cell against the image.” Explain what needs attention; do not invent a confidence score.
Failures
Say what failed, what happened to the person’s work and what they can do next. Only promise preserved work when that behaviour is established.
Models
Name active models, their jobs and exact sources. A tool without a model says “Models used: none”.

Accessibility

GOV.UK provides the foundation. Kettle’s adaptations and complete task flows still need checking.

  • Use the keyboard to reach every control, open details, choose files and correct results. Keep focus visible and in a useful place after actions.
  • The theme uses a 3px blue focus outline, a 2px offset and a white inner edge so focus remains visible on navy.
  • Keep labels, hints and errors associated with their controls. Do not rely on colour, an icon or motion alone.
  • Announce changing status politely and make failures available to assistive technology. Static examples need no live announcements.
  • Check zoom, narrow windows, reduced motion and forced colours. Controls should have at least a 44px hit area; long filenames and wide tables must not widen the page.
  • Check contrast on the actual surface, including hover, focus, disabled and error states. Do not assume a theme adaptation inherits an accessibility result.
